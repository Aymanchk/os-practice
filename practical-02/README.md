# ПР-2. Bash и системные вызовы

**Автор:** Эркинбеков Айман · **Дисциплина:** Операционные системы · **Вариант:** B

## Тема и цель

Научиться писать сценарии bash и увидеть, как обычная программа обращается
к ядру через системные вызовы, и сколько «лишних» вызовов добавляет
интерпретатор Python по сравнению с `cat`.

## Что сделано и как это работает

- **`report.sh`** принимает каталог с журналами и уровень (`ERROR` или `WARN`)
  и печатает таблицу «модуль → число сообщений» по убыванию. Ключ `--top N`
  оставляет только первые N строк. Без аргументов, при несуществующем каталоге
  или неверном уровне скрипт печатает справку и завершается с кодом 1.
  Внутри: `find` находит все `*.log`, `awk` вытаскивает модуль из строк нужного
  уровня, `sort | uniq -c | sort` считает и упорядочивает.
- **`hello.py`** читает файл блоками и печатает его размер.
- **strace** записал все системные вызовы `python3 hello.py` и `cat` на одном
  и том же файле, и их количество сравнено.
- Журналы `data/` (50 файлов, один пустой) создаёт `gen_logs.py` с фиксированным
  начальным числом, поэтому они одинаковы при каждом запуске. Контрольная
  сумма `cat data/*.log | md5sum` равна `93b24a51dea4a2f04800e793deb92105`
  и совпала с указанной преподавателем.

## Файлы

| Файл | За что отвечает |
| --- | --- |
| `README.md` | Отчёт |
| `run.sh` | Вся работа одной командой: данные, отчёты, проверка ошибок, strace |
| `report.sh` | Отчёт «модуль → число сообщений» по уровню ERROR или WARN |
| `hello.py` | Читает файл и выводит его размер |
| `gen_logs.py` | Создаёт 50 журналов в `data/` |
| `data/01.log` … `data/50.log` | Журналы вида `2026-02-14 10:31:02 ERROR module=net msg=...`; `25.log` намеренно пустой |
| `trace.txt` | Трассировка `strace` для `python3 hello.py data/01.log` |
| `trace_cat.txt` | Трассировка `strace` для `cat data/01.log` |
| `.gitignore` | Не добавлять в git папку `out/` с трассировками повторных запусков |

## Как запустить

Нужны `python3` и `strace` (`sudo apt install -y python3 strace`).

```bash
./run.sh
```

Или по отдельности, из папки `practical-02`:

```bash
./gen_logs.py
./report.sh data ERROR --top 3
./report.sh data WARN
./hello.py data/01.log
strace -f -y -o trace.txt python3 hello.py data/01.log > /dev/null
strace -f -y -o trace_cat.txt cat data/01.log > /dev/null
```

`-y` показывает рядом с номером дескриптора путь к файлу, так легко найти
вызовы, которые относятся именно к `data/01.log`.

## Пример вывода

Отчёты (Ubuntu 26.04.1 ARM64; в Docker-контейнере вывод такой же):

```text
$ ./report.sh data ERROR --top 3
Модуль  Сообщений
db      637
net     600
disk    321

$ ./report.sh data WARN
Модуль  Сообщений
net     933
disk    889
db      740
cache   647
api     461
auth    438
sched   215
fs      203
```

Больше всего ошибок у модуля `db`: генератор специально добавил в файл
`17.log` «аварию» из 120 ошибок `db` подряд.

Неверные аргументы:

```text
$ ./report.sh
Ошибка: неверное число аргументов
Использование: ./report.sh <каталог> <ERROR|WARN> [--top N]
$ echo $?
1
$ ./report.sh /nope ERROR
Ошибка: каталог не существует: /nope
$ ./report.sh data INFO
Ошибка: уровень должен быть ERROR или WARN
$ ./report.sh data ERROR --top abc
Ошибка: N должно быть положительным целым числом
```

Во всех случаях код возврата 1. `shellcheck report.sh run.sh` замечаний не выдаёт.

Размер файла:

```text
$ ./hello.py data/01.log
Размер: 19076 байт
$ stat -c '%s' data/01.log
19076
```

### Системные вызовы

Трассировки `trace.txt` и `trace_cat.txt` сняты в виртуальной машине
(Ubuntu Desktop 26.04.1 ARM64):

| Программа | Всего вызовов | Из них работают с `data/01.log` |
| --- | ---: | ---: |
| `python3 hello.py data/01.log` | 407 | 7: `openat`, `fstat`, `lseek`, `read` ×3, `close` |
| `cat data/01.log` | 144 | 7: `statx`, `openat`, `fstat`, `splice` ×3, `close` |

Из 407 вызовов Python собственно чтением данных заняты только 3 `read`: первый
прочитал все 19076 байт, два следующих вернули 0 (конец файла). Вместе с
открытием, проверками и закрытием файла: 7 вызовов. Остальные 400: запуск
интерпретатора: загрузка библиотек и модулей, поиск путей, настройка памяти.

`cat` вообще не вызывает `read`: он перекладывает данные через `splice`
прямо внутри ядра, без копирования в память программы.

В Docker-контейнере `run.sh` насчитал 361 и 157 вызовов: точное число зависит
от системы и окружения, но соотношение то же: у Python примерно в 2,5 раза
больше вызовов, а с файлом работают те же 7.

## Контрольные вопросы

**Почему нельзя обратиться к диску напрямую из пользовательской программы?**
Программа работает в пользовательском режиме процессора, где доступ к
устройствам запрещён. Иначе любая программа могла бы обойти права доступа
и испортить чужие данные. Поэтому программа просит ядро через системный вызов,
а ядро проверяет права и выполняет операцию.

**Что дороже: вызов функции или системный вызов, и почему?**
Системный вызов. Обычная функция остаётся в пользовательском режиме. При
системном вызове процессор переключается в режим ядра, ядро проверяет
аргументы, выполняет работу и возвращает управление обратно. Это на порядок
дороже.

## Выводы

- `report.sh` корректно строит отчёты и возвращает код 1 при неверных
  аргументах; переменные взяты в кавычки, поэтому скрипт работает и с путями
  с пробелами.
- Даже простая программа на Python делает сотни системных вызовов только для
  запуска интерпретатора; полезная работа с файлом: 7 из 407.
- `cat` на той же задаче делает в 2,8 раза меньше вызовов и копирует данные
  внутри ядра через `splice`.
