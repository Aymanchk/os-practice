## Кольцевой буфер и проверки

Буфер на 5 элементов - это список из 5 ячеек, индексы `head` и `tail` и счётчик `count`. Сам `Ring` блокировок не имеет: защиту ставит тот, кто им пользуется. Зато `Ring` проверяет свои инварианты и записывает нарушения в журнал:

- запись в полный буфер (переполнение);
- чтение из пустого буфера (опустошение).

Кроме журнала, программа проверяет:

- максимальное заполнение буфера не больше 5;
- каждый из 1000 элементов потреблён ровно один раз: нет повторов и нет потерянных элементов;
- после работы буфер пуст.

Производитель с номером k создаёт числа k, k+3, k+6 и так далее, так что вместе они создают числа от 0 до 999. Когда все производители закончили, главный поток кладёт в буфер по одному значению `STOP` для каждого потребителя, и потребители завершаются.

Проверка сделана в коде, а не «на глаз»: функция `run()` считает повторы и пропуски через `Counter`, а программа возвращает код 1, если хоть один инвариант нарушен. В `producer_consumer.py` интервал переключения потоков уменьшен (`sys.setswitchinterval(1e-6)`), чтобы потоки переключались чаще и ошибки проявлялись, если они есть.

## (а) Семафоры и мьютекс

Два семафора считают места: `empty` (свободные места, сначала 5) и `full` (занятые места, сначала 0). Производитель делает `empty.acquire()`, кладёт элемент под мьютексом и делает `full.release()`. Потребитель делает наоборот. Семафор берётся до мьютекса: если ждать семафор, держа мьютекс, потребитель мог бы заснуть на пустом буфере с занятым мьютексом, и производитель не смог бы положить элемент (взаимная блокировка). Под мьютексом только само добавление или извлечение элемента, поэтому критическая секция короткая.

```text
Вариант: семафоры и мьютекс
Производителей: 3, потребителей: 2
Размер буфера: 5
Создано элементов: 1000
Потреблено элементов: 1000
Потребители получили: 485, 515
Каждый элемент потреблён ровно один раз: True
Повторов: 0, потеряно: 0
Максимальное заполнение буфера: 5
Остаток в буфере после работы: 0
Нарушений буфера: 0
Время: 0.012 с
```

## (б) Мьютекс и условная переменная

Одна блокировка и две условные переменные `not_full` и `not_empty`, которые работают на этой блокировке. Производитель ждёт, пока буфер не полный, потребитель ждёт, пока он не пустой. Ожидание всегда в цикле `while`, потому что после пробуждения условие нужно проверить заново (см. раздел про `if` ниже).

Сколько элементов получил каждый потребитель, меняется от запуска к запуску. Это нормально: сумма всегда 1000. Чтобы убедиться, что корректность не случайность, каждый вариант запущен 20 раз подряд:

## Барьер

Класс `Barrier` написан на `Condition`. Каждый поток при вызове `wait` увеличивает счётчик ждущих. Последний пришедший поток обнуляет счётчик, увеличивает номер поколения `generation` и будит всех через `notify_all`. Остальные ждут в цикле `while generation == self.generation`. Номер поколения нужен, чтобы барьер можно было использовать снова на следующей фазе: быстрый поток, уже начавший следующую фазу, не перепутает её с прошлой.

Проверка: после работы программа просматривает журнал событий и убеждается, что ни один поток не начал фазу k+1 раньше, чем последний поток закончил фазу k.

```text
начал  фаза 1, поток 1
начал  фаза 1, поток 2
начал  фаза 1, поток 3
начал  фаза 1, поток 4
конец  фаза 1, поток 1
конец  фаза 1, поток 3
конец  фаза 1, поток 4
конец  фаза 1, поток 2
начал  фаза 2, поток 2
начал  фаза 2, поток 4
начал  фаза 2, поток 3
начал  фаза 2, поток 1
конец  фаза 2, поток 4
конец  фаза 2, поток 3
конец  фаза 2, поток 1
конец  фаза 2, поток 2
начал  фаза 3, поток 2
начал  фаза 3, поток 3
начал  фаза 3, поток 4
начал  фаза 3, поток 1
конец  фаза 3, поток 2
конец  фаза 3, поток 3
конец  фаза 3, поток 4
конец  фаза 3, поток 1
Барьер работает правильно: True
```

Порядок строк в выводе меняется от запуска к запуску, но последняя строка должна быть «Барьер работает правильно: True».

## Ожидание через if вместо while

В `wakeup_broken.py` два потребителя ждут пустой буфер. Производитель кладёт один элемент и вызывает `notify_all`, то есть будит обоих. Оба просыпаются и по очереди берут мьютекс. Первый забирает элемент. Второй уже проснулся, и из-за `if` вместо цикла он не проверяет условие заново, идёт дальше и читает из пустого буфера. В журнале появляется нарушение, этот потребитель получает `None`, а второй элемент потом остаётся в буфере, потому что его некому забрать.

```text
потребитель 1 получил: элемент 1
потребитель 2 получил: None
Нарушений: 1
  опустошение: чтение из пустого буфера
Остаток в буфере: 1
```

Код возврата у этой программы 1, и это ожидаемо: она специально ломается.

В `wakeup_fixed.py` вместо `if` стоит `while`. Второй потребитель после пробуждения видит, что буфер пуст, и снова засыпает до следующего элемента.

```text
потребитель 1 получил: элемент 1
потребитель 2 получил: элемент 2
Нарушений: 0
Остаток в буфере: 0
```

Файлы отличаются только строкой с ожиданием и строкой пояснения в начале, это видно командой `diff wakeup_broken.py wakeup_fixed.py`.

Замечание по названию. Строго говоря, «потерянное пробуждение» - это когда `notify` вызван раньше `wait` и сигнал пропал. Здесь пробуждение не потерялось, а стало бесполезным, потому что к моменту, когда потоку дали мьютекс, условие снова ложно. Лечится это одним способом: ждать только в цикле `while` и проверять условие под мьютексом.

## Контрольные вопросы

### Чем семафор со значением 1 отличается от мьютекса на практике?

У мьютекса есть владелец: поток, который его захватил, должен его и освободить. Мьютекс нужен только для взаимного исключения. У семафора владельца нет, `release()` может вызвать любой поток, поэтому семафор подходит и для сигналов между потоками, как `empty` и `full` в этой работе. Семафор можно случайно освободить лишний раз, и тогда его значение станет 2, а взаимное исключение сломается без ошибки. В Python `threading.Lock` технически можно освободить из другого потока, но по смыслу так не делают.

### Почему условную переменную нельзя использовать без мьютекса?

Проверка условия и засыпание должны быть одним неделимым действием. Без мьютекса потребитель мог бы проверить, что буфер пуст, потом производитель положил бы элемент и вызвал `notify`, а потребитель ещё не успел заснуть. Сигнал пропал бы, и потребитель заснул бы, хотя элемент уже лежит в буфере. Мьютекс защищает общие данные, по которым проверяется условие, а `wait` сам освобождает мьютекс и засыпает как одно действие. В Python `wait` без захваченной блокировки вызывает `RuntimeError`.

## Типичные ошибки, которых я избегал

- блокировки берутся через `with`, поэтому освобождаются и при исключении;
- `wait` вызывается только внутри цикла `while`;
- критическая секция короткая: семафоры берутся вне мьютекса, а под мьютексом только операция с буфером.

## Результат

Задача «производитель-потребитель» реализована двумя способами без `queue.Queue`. В каждом запуске все 1000 элементов потреблены ровно один раз, буфер не переполняется и не опустошается, а проверка сделана инвариантами в коде. Барьер на условной переменной выдерживает три фазы для четырёх потоков. Ошибка с `if` вместо `while` воспроизведена в `wakeup_broken.py` и исправлена в `wakeup_fixed.py`.
