# ПР-6. Синхронизация потоков

**Автор:** Эркинбеков Айман · **Дисциплина:** Операционные системы · **Вариант:** B

## Тема и цель

Реализовать задачу «производитель-потребитель» без готовой `queue.Queue` двумя
способами, проверить её корректность проверками в коде, написать барьер и
показать, что ломается, если ждать условие через `if`, а не через `while`.

## Что сделано и как это работает

- **Кольцевой буфер на 5 элементов** (`Ring` в `common.py`): список из 5 ячеек,
  индексы «голова» и «хвост» и счётчик. Сам буфер блокировок не имеет, но
  проверяет себя: запись в полный буфер и чтение из пустого попадают в журнал
  нарушений.
- **(а) Два семафора и мьютекс** (`SemaphoreBuffer`). Семафор `empty` считает
  свободные места (сначала 5), `full`: занятые (сначала 0). Производитель:
  `empty.acquire()` → положить под мьютексом → `full.release()`; потребитель:
  наоборот. Семафор берётся **до** мьютекса: иначе потребитель мог бы заснуть
  на пустом буфере, держа мьютекс, и производитель не смог бы ничего положить.
- **(б) Мьютекс и условные переменные** (`ConditionBuffer`). Одна блокировка и
  две условные переменные `not_full` и `not_empty`. Ожидание: всегда в цикле
  `while`: после пробуждения условие проверяется заново.
- **3 производителя, 2 потребителя, 1000 элементов.** Производитель k создаёт
  числа k, k+3, k+6, …, вместе ровно 0…999. Когда производители закончили,
  главный поток кладёт по одному `STOP` на каждого потребителя.
- **Проверка в коде, а не «на глаз».** Через `Counter` проверяется, что каждый
  элемент потреблён ровно один раз (нет повторов и потерь), буфер ни разу не
  переполнился и в конце пуст. Если что-то нарушено: код возврата 1. Чтобы
  ошибки проявлялись чаще, интервал переключения потоков уменьшен
  (`sys.setswitchinterval(1e-6)`).
- **Барьер** на условной переменной для 4 потоков и 3 фаз. Последний пришедший
  поток увеличивает номер «поколения» и будит всех; остальные ждут, пока номер
  не изменится. Номер поколения позволяет использовать барьер повторно.
  Программа проверяет по журналу событий, что никто не начал фазу k+1 раньше,
  чем все закончили фазу k.
- **`if` вместо `while`.** Два потребителя ждут пустой буфер; производитель
  кладёт один элемент и будит обоих (`notify_all`). Первый забирает элемент,
  а второй из-за `if` не проверяет условие заново и читает пустой буфер.

## Как запустить

Нужен только `python3`.

```bash

```

Или по отдельности:

```bash
./producer_consumer.py sem
./producer_consumer.py cond
./barrier_demo.py
./wakeup_broken.py
./wakeup_fixed.py
diff wakeup_broken.py wakeup_fixed.py
```

## Пример вывода и что он означает

Вывод снят в Ubuntu Desktop 26.04.1 ARM64 (UTM), Python 3.14.4, 4 ядра.

**(а) Семафоры и мьютекс:**

```text
Вариант: семафоры и мьютекс
Производителей: 3, потребителей: 2
Размер буфера: 5
Создано элементов: 1000
Потреблено элементов: 1000
Потребители получили: 485, 515
Каждый элемент потреблён ровно один раз: True
Повторов: 0, потеряно: 0
Максимальное заполнение буфера: 5
Остаток в буфере после работы: 0
Нарушений буфера: 0
Время: 0.012 с
```

**(б) Мьютекс и условная переменная**: то же самое, потребители получили
614 и 386 элементов, время 0.009 с.

Сколько получил каждый потребитель, меняется от запуска к запуску, это
нормально, сумма всегда 1000. Чтобы убедиться, что корректность не случайна,
каждый вариант запущен 20 раз подряд:

```text
sem: запусков 20, сбоев 0
cond: запусков 20, сбоев 0
```

**Барьер** (начало и конец):

```text
начал  фаза 1, поток 1
...
конец  фаза 1, поток 2
начал  фаза 2, поток 2
...
конец  фаза 3, поток 1
Барьер работает правильно: True
```

Все «конец фаза 1» стоят раньше любого «начал фаза 2», потоки ждут друг
друга на барьере. Порядок потоков внутри фазы меняется от запуска к запуску.
Полный вывод: в `evidence/barrier.txt`.

**`if` вместо `while`** (код возврата 1: программа ломается специально):

```text
потребитель 1 получил: элемент 1
потребитель 2 получил: None
Нарушений: 1
  опустошение: чтение из пустого буфера
Остаток в буфере: 1
```

**Исправлено через `while`:**

```text
потребитель 1 получил: элемент 1
потребитель 2 получил: элемент 2
Нарушений: 0
Остаток в буфере: 0
```

Файлы отличаются только строкой ожидания и строкой описания, это видно
командой `diff`.

Замечание о названии. Строго говоря, «потерянное пробуждение» это когда
`notify` пришёл раньше `wait`, и сигнал пропал. Здесь пробуждение не пропало,
а стало бесполезным: к моменту, когда потоку достался мьютекс, условие снова
ложно. Лечится одинаково: ждать только в цикле `while` под мьютексом.

## Контрольные вопросы

**Чем семафор со значением 1 отличается от мьютекса на практике?** У мьютекса
есть владелец: освобождает его тот же поток, что захватил, и он нужен только
для взаимного исключения. У семафора владельца нет, `release()` может вызвать
любой поток, поэтому семафор подходит и для сигналов между потоками (как
`empty` и `full` здесь). Зато семафор можно случайно освободить лишний раз,
его значение станет 2, и взаимное исключение тихо сломается.

**Почему условную переменную нельзя использовать без мьютекса?** Проверка
условия и засыпание должны быть одним неделимым действием. Без мьютекса
потребитель мог бы увидеть пустой буфер, производитель тут же положил бы
элемент и вызвал `notify`, а потребитель заснул бы уже после этого, и сигнал
пропал бы. `wait` атомарно освобождает мьютекс и засыпает. В Python `wait` без
захваченной блокировки вызывает `RuntimeError`.

## Выводы

- Оба варианта ограниченного буфера корректны: в каждом из 20 запусков все
  1000 элементов потреблены ровно один раз, буфер не переполнялся.
- Блокировки берутся через `with`, поэтому освобождаются и при исключении.
- Критические секции короткие: под мьютексом только операция с буфером.
- Ожидание на условной переменной всегда пишется циклом `while`; с `if` ошибка
  воспроизводится в каждом запуске.
