## Тема и цель

Освоить файловую иерархию, права доступа, ссылки и метаданные; понять, как
файлы размещаются на диске. На уровне B: написать инкрементальное резервное
копирование и поиск дубликатов с заменой на жёсткие ссылки, сравнить на модели
три способа размещения файла и довести настоящую ext4 до состояния «диск полон,
а место есть».

Связь с лекцией 12: файл, каталог, inode, методы размещения, права доступа
Linux, монтирование.

## Что сделано и как это работает

- **`backup.sh`**: инкрементальная резервная копия каталога.
  - Файл копируется, только если в копии его нет или у него другой размер или
    время изменения (`stat -c '%s %Y'`). Повторный запуск без изменений ничего не
    копирует.
  - Копирование через `cp -p`: сохраняются права, временные метки и (от root)
    владелец. Без этого следующий запуск считал бы все файлы изменёнными, а права
    `640` превратились бы в `644`. Права каталогов переносятся `chmod --reference`.
  - Символические ссылки копируются как ссылки (`cp -P`), а не как файлы, на
    которые они указывают.
  - Журнал `КОПИЯ/.backup.log`: время, что сделано с каждым файлом, итог.
  - Файл, удалённый в источнике, из копии **не удаляется**, а только отмечается в
    журнале: случайный `rm` в рабочей папке не должен уничтожить и резервную копию.
  - `./backup.sh --restore КОПИЯ КУДА`: восстановление через `cp -a`, журнал копии
    в восстановленные данные не попадает.
  - Имена с пробелами работают: `find -print0` и `read -d ''`.
- **`dedup.py`**: дубликаты по содержимому.
  - Сначала файлы группируются по размеру: файлы разного размера совпасть не
    могут, и SHA-256 считается только внутри групп одного размера.
  - Если файлы уже один inode (жёсткие ссылки друг на друга), второй раз они не
    считаются. Пустые файлы не объединяются.
  - Замена атомарная: ссылка создаётся под временным именем (`os.link`) и
    переименовывается поверх дубликата (`os.replace`). Если программа упадёт
    посередине, файл не пропадёт.
  - `-n`: только показать, ничего не менять. Итог: сколько байт сэкономлено.
- **`alloc.py`**: модель диска из 512 блоков и три способа хранения файла:
  непрерывный (начало и длина), связанный (указатель на следующий блок в каждом
  блоке) и индексный (номера блоков в отдельном индексном блоке). Один и тот же
  поток из 400 операций создания и удаления (`seed = 12`) прогоняется для всех трёх.
- **`fsimage.sh`**: настоящая ext4 в файле: `dd` → `mkfs.ext4 -N 128` →
  `mount -o loop`, создание пустых файлов до исчерпания inode. Всё удаляется в
  конце, даже при ошибке (`trap`).
- **`links_demo.sh`**: жёсткая и символическая ссылка, `ls -li` до и после
  удаления исходного файла (для контрольных вопросов).
- **`check_pr12.py`**: 26 проверок: сравнение деревьев источника, копии и
  восстановленных данных по содержимому, правам, времени и ссылкам; dedup на
  наборе с ловушками (тот же размер с другим содержимым, уже связанные файлы,
  пустые файлы); суммы блоков в модели.

## Как запустить

Нужны Linux (GNU coreutils), `python3`; для `fsimage.sh` ещё `e2fsprogs` и права root.

```bash
sudo ./run.sh
```

В Docker на macOS или Windows:

```bash
docker run --rm -it --privileged -v "$PWD":/work -w /work ubuntu:26.04 bash
apt-get update && apt-get install -y python3 e2fsprogs
```

## 1. Инкрементальное резервное копирование

Из `evidence/run.txt` (пути временных каталогов сокращены):

```text
== backup.sh: первый запуск
скопировано 2, без изменений 0, пропало в источнике 0
== backup.sh: повторный запуск
скопировано 0, без изменений 2, пропало в источнике 0
== backup.sh: после изменений
скопировано 2, без изменений 1, пропало в источнике 0
== журнал
  == резервная копия .../src -> .../bak
  новый    report.txt
  новый    docs/plan.txt
  итог: скопировано 2, без изменений 0, пропало в источнике 0
  == резервная копия .../src -> .../bak
  итог: скопировано 0, без изменений 2, пропало в источнике 0
  == резервная копия .../src -> .../bak
  изменён  report.txt
  новый    docs/new.txt
  итог: скопировано 2, без изменений 1, пропало в источнике 0
== права в копии
  -rw-r----- .../bak/report.txt
== восстановление
восстановлено в .../restored: 3 файлов
```

- Второй запуск ничего не скопировал: скрипт идемпотентен.
- После изменения одного файла и добавления другого скопированы ровно эти два.
- Права `640` (`-rw-r-----`) в копии сохранились.

Почему не просто `cp`: обычный `cp` ставит копии текущее время и права по
`umask`. Тогда сравнение по mtime на следующем запуске сочло бы изменёнными все
файлы, а закрытый файл (`600`) в копии стал бы читаемым для всех (`644`).

## 2. Дубликаты и жёсткие ссылки

```text
== dedup.py -n
    50000 Б  a/photo.jpg
             = b/photo (1).jpg
             = b/photo-copy.jpg
групп дубликатов: 1, лишних копий: 2, можно сэкономить: 100000 Б (97.7 КБ)
== dedup.py
...
групп дубликатов: 1, лишних копий: 2, сэкономлено: 100000 Б (97.7 КБ)
  inode 48422, ссылок 3: photo.jpg
  inode 48422, ссылок 3: photo (1).jpg
  inode 48422, ссылок 3: photo-copy.jpg
```

После замены три имени указывают на один inode (48422), счётчик ссылок 3, данные
на диске хранятся один раз. Место освободится только тогда, когда будут удалены
все три имени.

Ограничение метода: жёсткие ссылки делят не только данные, но и сам файл. Если
потом изменить `photo-copy.jpg`, изменятся и остальные два. Для фотоархива это
нормально, для рабочих документов лучше копирование при записи (reflink в Btrfs
и XFS).

## 3. Три способа размещения файла

`evidence/alloc.txt`:

```text
Диск 512 блоков, 400 операций (216 созданий, 184 удалений), размер файла 1..30 блоков, seed 12
                                            непрерывный    связанный    индексный
создано файлов                                      189          198          194
не удалось создать                                   27           18           22
  из них при достаточном свободном месте             27            0            0
файлов на диске в конце                              27           30           28
блоков данных                                       411          477          446
служебных блоков                                      0            0           28
свободно блоков                                     101           35           38
свободных участков (дыр)                             13            8            6
самая большая дыра                                   23            9           14
чтений для k-го блока, среднее                     1.00        10.41         2.00
чтений для k-го блока, худшее                         1           30            2
кусков на файл, среднее                            1.00         2.90         2.82
```

| | Непрерывное | Связанное | Индексное |
| --- | --- | --- | --- |
| Произвольный доступ к k-му блоку | **1 чтение**: адрес = начало + k | **k + 1 чтений**: пройти цепочку | **2 чтения**: индекс + блок |
| Внешняя фрагментация | **есть**: 27 отказов при 101 свободном блоке, самая большая дыра 23 | нет | нет |
| Служебные данные | 0 (начало и длина в каталоге) | указатель внутри каждого блока | 1 индексный блок на файл (28 блоков) |
| Последовательное чтение на HDD | лучшее: файл одним куском | файл в среднем из 2,9 кусков | 2,8 куска |
| Рост файла | трудно: соседние блоки могут быть заняты | легко | легко, пока хватает индекса |

- Непрерывное размещение быстрее всех читает, но страдает от внешней
  фрагментации: в конце на диске 101 свободный блок, но разбит на 13 дыр, и все 27
  отказов случились при достаточном общем свободном месте.
- Связанное размещение использует каждый свободный блок, но произвольный доступ к
  концу файла из 30 блоков стоит 30 чтений, а одна испорченная ссылка теряет весь
  хвост файла.
- Индексное размещение даёт произвольный доступ за 2 чтения ценой одного
  служебного блока на файл. Из-за этого блока оно иногда отказывает раньше
  связанного (22 против 18), когда для файла хватило бы данных, но не данных и индекса.
- ext4 совмещает подходы: индексная структура (дерево экстентов в inode), но каждый
  элемент описывает непрерывный кусок (экстент), поэтому крупный файл занимает
  несколько кусков и читается почти так же быстро, как непрерывный.

```text
  создано 75 файлов, занято inode: 87

  Filesystem      Size  Used Avail Use% Mounted on
  /dev/loop0       12M  152K   11M   2% /mnt/pr12
  Filesystem     Inodes IUsed IFree IUse% Mounted on
  /dev/loop0        128   128     0  100% /mnt/pr12

== 5. В существующий файл писать можно: блоки есть, новый inode не нужен
  f0: 4194304 Б
  mkdir: mkdir: No space left on device

  touch again: ok, свободно inode: 0
```

- Каждый новый файл забирает ровно один inode: занято 12 (служебные: корень,
  `lost+found`, журнал и зарезервированные), после 25 файлов 37, после 100 файлов 112.
- После 116 файлов `touch` пишет **«No space left on device»**, хотя `df -h`
  показывает занятыми 2% (152 КБ из 12 МБ). Пустой файл блоков данных не занимает,
  но без inode файла не бывает: в inode хранятся владелец, права, размер, время и
  адреса блоков. Число inode задаётся при `mkfs` (`-N`) и потом не растёт.
- В уже существующий файл можно записать 4 МБ: ему нужны только блоки, а их много.
  Каталог создать нельзя: каталог тоже файл, ему тоже нужен inode.
- `df -h` сообщает о свободном месте, а о свободных inode сообщает только `df -i`.
  На реальных серверах это случается из-за миллионов мелких файлов (кэши, сессии,
  почтовые очереди).
- Размер 12 МБ вместо 16: часть образа ext4 сразу забирает под журнал, таблицы
  inode и битовые карты.

символическая «сломалась»: путь, на который она указывает, больше не существует.

## Контрольные вопросы

**Почему нельзя создать жёсткую ссылку на файл в другой файловой системе?**
Жёсткая ссылка это запись в каталоге «имя → номер inode». Номер inode имеет
смысл только внутри своей файловой системы: inode 48403 на одном разделе и inode
48403 на другом это разные файлы. Записать в каталог ссылку на чужой inode
нельзя, поэтому ядро отвечает `Invalid cross-device link` (раздел 5). По той же
причине `dedup.py` проверяет, что оригинал и дубликат на одном устройстве.
Символическая ссылка хранит путь, а путь может вести куда угодно.

**Что физически удаляется при `rm`, если на файл есть две жёсткие ссылки?**
Только одна запись в каталоге (имя), и счётчик ссылок в inode уменьшается с 2 до
1. Сам inode и блоки данных остаются, файл доступен по второму имени. Данные
освобождаются, только когда счётчик ссылок становится 0 **и** файл не открыт ни
одним процессом. Поэтому `rm` и называется `unlink`.

## Типичные ошибки, которых я избегал

- Символическая и жёсткая ссылка не путаются: жёсткая указывает на inode,
  символическая на путь (раздел 5).
- Нигде нет `chmod 777`: в копии и при восстановлении права переносятся как были.
- Копия делается `cp -p`/`cp -a`, а не голым `cp`, поэтому права и время не теряются,
  а инкрементальность работает.
- `backup.sh` идемпотентен и при повторном запуске не портит копию.
- dedup не объединяет файлы с одинаковым размером, но разным содержимым, и не
  считает дважды файлы, которые уже связаны.

## Выводы

- Инкрементальная копия по размеру и mtime работает, только если копирование
  сохраняет время и права; тогда повторный запуск копирует 0 файлов.
- Замена дубликатов жёсткими ссылками экономит место без изменения содержимого,
  но только в пределах одной файловой системы.
- Непрерывное размещение даёт самый быстрый доступ, но теряет место на внешней
  фрагментации; связанное не фрагментируется, но произвольный доступ стоит k + 1
  чтений; индексное даёт доступ за 2 чтения ценой индексного блока. Реальные ФС
  (ext4) используют экстенты, соединяя достоинства первого и третьего.
- Место на ФС кончается двумя способами: блоки и inode. При исчерпании inode
  `touch` пишет «No space left on device» при 98% свободных блоков.
