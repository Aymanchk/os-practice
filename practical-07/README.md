# ПР-7. Межпроцессное взаимодействие

**Автор:** Эркинбеков Айман · **Дисциплина:** Операционные системы · **Вариант:** B

## Тема и цель

Организовать обмен данными между процессами через разные механизмы IPC:
именованные каналы (FIFO), Unix-сокеты, `Pipe` и разделяемую память, и
сравнить их по скорости и по тому, кто отвечает за синхронизацию.

## Что сделано и как это работает

- **Сервис «калькулятор».** Клиент присылает выражение, сервер считает и
  отвечает. Выражение разбирается через `ast` (без `eval()`), разрешены числа,
  `+ - * / // % **`, скобки и унарный минус.
- **Клиент-сервер на FIFO.** Два именованных канала: `/tmp/pr07_request.fifo`
  для запросов и `/tmp/pr07_response.fifo` для ответов. Клиенты обслуживаются
  по очереди: канал ответов один, и два одновременных клиента могли бы получить
  чужие ответы. `open()` у FIFO ждёт, пока откроют другой конец, это нормальное
  поведение, а не зависание. Чтобы не ждать вечно, если другой стороны нет,
  клиент ждёт сервер (и его ответ) не дольше 5 секунд, а сервер ждёт, пока
  клиент заберёт ответ, тоже не дольше 5 секунд.
- **Тот же сервис на Unix-сокете** `/tmp/pr07.sock` с несколькими одновременными
  клиентами, **по процессу на клиента**: сервер на каждое подключение делает
  `fork`, и клиента обслуживает отдельный дочерний процесс. PID клиента сервер
  узнаёт через `SO_PEERCRED`. Чтобы параллельность была видна, ответ задерживается
  на 0,3 с. `socket_clients.py` запускает 5 клиентов одновременно, каждый в своём
  процессе.
- **Сравнение механизмов.** `ipc_bench.py` передаёт массив из 10 млн чисел int64
  (80 МБ) от родителя ребёнку через `Pipe`, FIFO, Unix-сокет и
  `multiprocessing.shared_memory`. Время: от начала передачи до сообщения
  ребёнка «получено», 3 повтора, медиана. Целостность проверяется по SHA-256.
- **Уборка.** Серверы при остановке (Ctrl+C, `kill -TERM`, команда `!stop`)
  удаляют свои FIFO и сокет, `ipc_bench.py` удаляет сегменты разделяемой памяти.
  Если сегмент не помещается в `/dev/shm`, замер пропускается с сообщением
  (иначе процесс погиб бы от сигнала SIGBUS и оставил сегмент в памяти).

## Как запустить

Нужен только `python3`.

```bash
./run.sh
```

### Вручную, в двух терминалах

FIFO. Терминал 1:

```bash
./fifo_server.py
```

Терминал 2:

```bash
./fifo_client.py "2+2"
./fifo_client.py "(3+4)*5"
./fifo_client.py '!stop'
```

Unix-сокет. Терминал 1 (остановка: Ctrl+C):

```bash
./socket_server.py
```

Терминал 2:

```bash
./socket_clients.py
./socket_client.py "2**10" "7//2"
```

Замеры: `./ipc_bench.py`. Для проверки уборки после всего:

```bash
ls /tmp/pr07* /dev/shm
```

### Сравнение механизмов (ВМ, 80 МБ, медиана 3 повторов)

| Механизм | Синхронизация со стороны программиста | Объём данных | Время передачи, с | Скорость, МБ/с |
| --- | --- | ---: | ---: | ---: |
| Pipe (multiprocessing) | нет, ядро блокирует процессы | 80 МБ | 0.0327 | 2449 |
| FIFO | нет, ядро блокирует процессы | 80 МБ | 0.0472 | 1696 |
| Unix-сокет | нет, ядро блокирует процессы | 80 МБ | 0.0144 | 5536 |
| Разделяемая память, новый сегмент | да, нужен Event или семафор | 80 МБ | 0.0173 | 4631 |
| Разделяемая память, сегмент создан заранее | да, нужен Event или семафор | 80 МБ | 0.0023 | 34223 |

Во всех 15 передачах `данные совпали: True`. Полный вывод: в `evidence/ipc_bench.txt`.

После проверки исправления (закрытие лишних концов каналов и тайм-ауты)
`ipc_bench.py` снова запущен в Docker. Порядок механизмов тот же: сокет
0.0091 с, Pipe 0.0166 с, разделяемая память 0.0191 с и 0.0027 с (сегмент
заранее), FIFO 0.0317 с. Измеряемая часть кода при исправлении не менялась.

**Почему так:**

- Pipe, FIFO и сокет копируют данные дважды: из памяти отправителя в буфер ядра
  и из буфера ядра в память получателя. Ядро само блокирует писателя, когда
  буфер полон, и читателя, когда он пуст, синхронизацию программист не пишет.
- Разделяемая память отображена в адресное пространство обоих процессов:
  получатель читает данные на месте, без копирования через ядро. Но ядро не
  знает, когда данные готовы, поэтому синхронизация лежит на программисте (здесь
  ребёнок ждёт `Event`).
- Строка «новый сегмент» включает создание сегмента и выделение ядром 80 МБ:
  поэтому для разовой передачи выигрыш небольшой. Строка «создан заранее»
  показывает саму передачу: одно копирование в память, в 6 раз быстрее сокета.
  Разделяемая память выгодна, когда сегмент живёт долго и данные в нём
  читают и обновляют многократно.

## Контрольные вопросы

**Почему разделяемая память самый быстрый и самый опасный механизм IPC?**
Быстрый, потому что данные не копируются через ядро: после настройки процессы
работают с одной и той же памятью как с обычной. Опасный, потому что ядро
ничего не синхронизирует: если один процесс читает, пока другой пишет, данные
окажутся прочитаны наполовину, и такие ошибки проявляются нерегулярно. Кроме
того, сегмент живёт в `/dev/shm`, пока его явно не удалят (`unlink`), даже если
все процессы уже завершились.

**Что произойдёт при записи в pipe, у которого закрыты все читающие концы?**
Процесс получит сигнал SIGPIPE и по умолчанию завершится. Если сигнал
игнорируется или перехвачен, `write` вернёт ошибку `EPIPE`. Python игнорирует
SIGPIPE, поэтому в выводе исключение `BrokenPipeError`.

## Выводы

- Механизм IPC выбирают по объёму данных и по тому, кто отвечает за
  синхронизацию: каналы и сокеты проще и безопаснее, разделяемая память
  быстрее, но требует своей синхронизации.
- Ненужные концы каналов нужно закрывать: иначе читатель не получит EOF, а если
  другой процесс упадёт, оставшийся будет ждать вечно. В `ipc_bench.py`
  родитель закрывает концы ребёнка сразу после `start()`, и все ожидания идут
  с тайм-аутом.
- Блокировка при открытии FIFO: нормальное поведение; от «вечного» ожидания
  защищает тайм-аут.
- После работы не остаётся FIFO, сокетов и сегментов в `/dev/shm`.
