## Цель работы

## Файлы

- `calc.py` - вычисление выражений без `eval()`: выражение разбирается через `ast`, разрешены числа, `+ - * / // % **`, скобки и унарный минус.
- `ipc_common.py` - пути к FIFO и сокету, функция открытия FIFO на запись с тайм-аутом.
- `fifo_server.py`, `fifo_client.py` - клиент и сервер на двух именованных каналах.
- `socket_server.py`, `socket_client.py` - клиент и сервер на Unix-сокете.
- `socket_clients.py` - запускает 5 клиентов одновременно, каждый в своём процессе.
- `ipc_bench.py` - передача массива из 10 миллионов чисел разными способами и замеры.
- `broken_pipe_demo.py` - запись в pipe без читателей.
- `evidence/` - вывод запусков.

## Как запустить

Клиент и сервер запускаются в двух терминалах.

FIFO. В первом терминале:

```bash
./fifo_server.py
```

Во втором терминале:

```bash
./fifo_client.py "2+2"
./fifo_client.py "(3+4)*5"
./fifo_client.py '!stop'
```

Команда `!stop` останавливает сервер. Сервер также останавливается по Ctrl+C и по `kill -TERM`.

Unix-сокет. В первом терминале:

```bash
./socket_server.py
```

Во втором терминале:

```bash
./socket_clients.py
./socket_client.py "2**10" "7//2"
```

Сервер сокета останавливается по Ctrl+C. Замеры и проверка очистки:

```bash
./ipc_bench.py
```

## Клиент и сервер на FIFO

Используются два именованных канала: `/tmp/pr07_request.fifo` для запросов и `/tmp/pr07_response.fifo` для ответов. Сервер открывает канал запросов на чтение, и `open()` ждёт, пока клиент не откроет его на запись. Клиент пишет строку с выражением и закрывает канал, потом открывает канал ответов на чтение и ждёт. Сервер читает строку, считает через `calc.py`, открывает канал ответов на запись (это тоже ждёт читателя) и пишет ответ.

Клиенты работают по очереди. Канал ответов один, и если бы два клиента ждали ответ одновременно, они могли бы получить чужие ответы. Эту проблему решает версия на сокетах.

Блокировка при открытии FIFO это нормальное поведение, а не зависание: пока другой конец не открыт, `open()` не возвращается. Чтобы программа не висела бесконечно, если другой стороны нет, в `ipc_common.py` есть функция `open_for_writing`. Она открывает FIFO с флагом `O_NONBLOCK` и ждёт читателя не больше 5 секунд.

При остановке сервер удаляет оба FIFO в блоке `finally`.

Клиент, когда сервер не запущен:

```text
Сервер не запущен: нет файла /tmp/pr07_request.fifo
```

## Клиент и сервер на Unix-сокете

Сервер принимает подключения на сокете `/tmp/pr07.sock`. Для каждого подключения запускается свой поток (`ThreadingMixIn`), поэтому клиенты обслуживаются одновременно. ### Выводы по замерам

- Pipe, FIFO и сокет: данные копируются дважды, из памяти отправителя в буфер ядра и из буфера ядра в память получателя. Ядро само блокирует писателя, когда буфер полон, и читателя, когда он пуст, поэтому синхронизацию программист не пишет.
- Разделяемая память: сегмент отображён в адресное пространство обоих процессов, и получатель читает данные на месте, без копирования через ядро. Родитель один раз копирует массив в сегмент. Но ядро ничего не знает о том, когда данные готовы, поэтому синхронизацию делает программист. В программе для этого используется `Event`: ребёнок ждёт его и только потом читает сегмент.
- Для разделяемой памяти в таблице две строки. В первой замер включает создание сегмента и выделение ядром 80 МБ памяти. Во второй сегмент уже создан, а ребёнок уже подключён к нему. Строка с заранее созданным сегментом самая быстрая: передача сводится к одному копированию в память. Для разового переноса выигрыш меньше, потому что создание сегмента тоже стоит времени. Главная выгода разделяемой памяти там, где сегмент живёт долго и данные в нём читают и обновляют много раз.
- Если считать по числу копирований и переходов в ядро: у pipe, FIFO и сокета каждая порция данных проходит через системные вызовы `write` и `read`, а у разделяемой памяти после настройки обращения идут как к обычной памяти.

## Запись в pipe без читателей

`broken_pipe_demo.py` создаёт pipe, закрывает читающий конец и пытается писать:

```text

Читающих концов нет, запись завершилась ошибкой EPIPE
```

## Контрольные вопросы

### Почему разделяемая память - самый быстрый и самый опасный механизм IPC?

Самый быстрый, потому что данные не копируются через ядро: после настройки процессы обращаются к одной и той же области памяти как к обычной. Самый опасный, потому что ядро ничего не синхронизирует. Если два процесса одновременно пишут в сегмент или один читает, пока другой пишет, получится гонка: данные перемешаются или будут прочитаны не до конца, и такие ошибки проявляются нерегулярно. Синхронизацию (семафоры, `Event`) нужно написать самому. Кроме того, сегмент живёт в `/dev/shm`, пока его не удалят через `unlink`, даже если все процессы уже завершились.

### Что произойдёт при записи в pipe, у которого закрыты все читающие концы?

Процесс получит сигнал SIGPIPE, и по умолчанию он завершится. Если сигнал игнорируется или перехвачен, `write` вернёт ошибку `EPIPE`. Python игнорирует SIGPIPE, поэтому в выводе выше появилось исключение `BrokenPipeError`.

## Типичные ошибки, которых я избегал

- конец pipe, который процессу не нужен, закрывается: писатель в `ipc_bench.py` закрывает FIFO и делает `shutdown` у сокета, иначе читатель никогда не получил бы конец данных (EOF);
- блокировка при открытии FIFO принята за нормальное поведение, а для случая «другой стороны нет» сделан тайм-аут вместо вечного ожидания;
- разделяемая память не используется без синхронизации: ребёнок ждёт `Event` и только потом читает.
