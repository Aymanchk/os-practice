# ПР-8. Взаимоблокировки и алгоритм банкира

**Автор:** Эркинбеков Айман · **Дисциплина:** Операционные системы · **Вариант:** B

## Тема и цель

Воспроизвести взаимоблокировку (deadlock), реализовать алгоритм банкира и
обнаружение циклов в графе ожидания. Написать блокировку, которая сама
замечает цикл ожидания, и решить задачу об обедающих философах двумя способами.

## Что сделано и как это работает

- **Алгоритм банкира** (`banker.py`). Состояние читается из файла:
  `Available`, `Allocation`, `Max`; потребность `Need = Max − Allocation`.
  - *Проверка безопасности:* `Work = Available`; ищем незавершённый процесс с
    `Need ≤ Work`, «завершаем» его, `Work += Allocation[i]`; повторяем. Если
    завершились все: состояние безопасное, порядок завершения и есть безопасная
    последовательность. Иначе: `UNSAFE`.
  - *Запрос `request(pid, vector)`* (из stdin, строки вида `P1 1 0 2`):
    больше `Need`: ошибка; больше `Available`: процесс ждёт; иначе пробная
    выдача и проверка безопасности; если стало небезопасно: **откат** к
    сохранённому состоянию и отказ.
- **Детектор по журналу** (`deadlock_detector.py`). Журнал из строк
  `acquire|wait|release поток ресурс`, ресурсы единичные. После каждого события
  строится **граф ожидания**: ребро `T1 → T2`, если T1 ждёт ресурс, который
  держит T2. Цикл ищется обходом в глубину (`waitgraph.py`). Граф именно
  ожидания, а не распределения: поток, который только держит ресурс, рёбер не
  имеет и в цикл не попадёт, ложных срабатываний нет.
- **TrackedLock** (`tracked_lock.py`): обёртка над `threading.Lock`, которая
  ведёт граф ожидания в реальном времени. Перед тем как заснуть, поток
  записывает, чего ждёт, и ищет цикл. Если цикл замкнулся: вместо зависания
  бросается `DeadlockError` с описанием цепочки. Проверка и засыпание делаются
  под одной `Condition`, поэтому граф не может измениться между ними.
- **`deadlock.py`**: настоящая взаимоблокировка: T1 берёт `lock_a`, потом
  `lock_b`, а T2: наоборот. Приложена как есть, она зависает. Пауза между
  захватами нужна только для того, чтобы deadlock повторялся в каждом запуске;
  причина: разный порядок захвата.
- **Обедающие философы** (`philosophers.py`), три режима:
  - `naive`: сначала левая вилка, потом правая: deadlock;
  - `ordered`: вилки пронумерованы, сначала берётся вилка с меньшим номером;
  - `limit`: за столом не больше 4 философов из 5 (семафор N−1).
  Программа считает, сколько раз поел каждый, и сама определяет deadlock: у всех
  по одной вилке, никто не ест, и так несколько проверок подряд.
- **`check_pr8.py`** проверяет всё сразу: банкира: полным перебором порядков
  (400 случайных состояний и 400 запросов, включая точность отката), DFS:
  другим способом на 500 случайных графах и 500 журналах, TrackedLock: 20 раз,
  философов: во всех режимах.

## Как запустить

Нужен только `python3` (и `timeout` из coreutils, он есть в Ubuntu всегда).

```bash
./run.sh
```

Или по отдельности:

```bash
./banker.py bank1.txt --all -r < requests1.txt
./banker.py bank2.txt
./deadlock_detector.py events_deadlock.log
./deadlock_detector.py events_ok.log
./deadlock.py --tracked
./philosophers.py all 3
./check_pr8.py
```

**Как убедиться, что `deadlock.py` зависает.** Запустить `./deadlock.py` и
подождать: после строк «хочет» ничего не происходит, выйти: Ctrl+C. Надёжнее
через `timeout`: код возврата 124 значит, что программа не завершилась сама
за 5 секунд.

```bash
timeout 5 ./deadlock.py; echo $?
./deadlock.py --dump 3     # через 3 с напечатать, где ждёт каждый поток
```

Повторы философов (как получен `evidence/philosophers_repeat.txt`):

```bash
for m in naive ordered limit; do
  n=0; for i in $(seq 10); do ./philosophers.py "$m" 2 | grep -q ВЗАИМОБЛОКИРОВКА && n=$((n+1)); done
  echo "$m: запусков 10, взаимоблокировок $n"
done
```

## Четыре условия взаимоблокировки

1. **Взаимное исключение**: вилкой или блокировкой владеет один поток.
2. **Удержание и ожидание**: поток держит один ресурс и ждёт другой.
3. **Отсутствие вытеснения**: ресурс нельзя отобрать силой.
4. **Циклическое ожидание**: замкнутая цепочка «каждый ждёт следующего».

В `deadlock.py` и `naive` выполнены все четыре. `ordered` (и исправление
`deadlock.py` через единый порядок: сначала `lock_a`, потом `lock_b`) нарушает
**условие 4**. В `limit` цикл тоже не может замкнуться: при 4 философах и 5
вилках хотя бы один всегда возьмёт обе. `TrackedLock` ничего не нарушает
заранее, а ловит момент, когда условие 4 вот-вот выполнится.

## Контрольные вопросы

**Почему упорядочивание захвата ресурсов исключает deadlock?** Если все
ресурсы пронумерованы и каждый поток берёт их только по возрастанию номеров,
то поток, ждущий ресурс k, держит только ресурсы с номерами меньше k. В цепочке
«кто кого ждёт» номера только растут, и замкнуться в круг она не может, поэтому нет
циклического ожидания.

**Почему алгоритм банкира редко применяется в универсальных ОС?**
- Нужно заранее знать максимальную потребность каждого процесса, а программа
  обычно этого не знает.
- Он предполагает фиксированное число процессов и ресурсов, а в ОС процессы
  постоянно появляются и исчезают.
- Блокировки, файлы и сокеты плохо укладываются в вектор «экземпляров ресурса».
- Проверка стоит порядка `m · n²` действий на каждый запрос.
- Он слишком осторожен: отказывает даже тогда, когда deadlock мог и не случиться.

Поэтому Linux и Windows в пользовательские взаимоблокировки не вмешиваются и
оставляют их программисту (порядок захвата, тайм-ауты, детекторы).

## Выводы

- Deadlock не случайный сбой, а следствие четырёх одновременно выполненных
  условий; убрать любое: убрать deadlock. Добавление `sleep` его не лечит,
  только меняет частоту.
- Банкир корректен: `Work` увеличивается на `Allocation[i]`, откат точный,
  результаты на `bank1`/`bank2` подтверждены полным перебором.
- Цикл ищется в графе ожидания, поэтому детектор не даёт ложных срабатываний.
- Единый порядок захвата и ограничение числа участников надёжно устраняют
  взаимоблокировку философов.
