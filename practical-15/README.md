**Автор:** Эркинбеков Айман · **Дисциплина:** Операционные системы · **Вариант:** B

## Тема и цель

Изолировать приложение в контейнере, ограничить ему ресурсы и понять, чем
контейнер отличается от виртуальной машины. На уровне B: Dockerfile для
мини-сервиса из ПР-7, проброс порта, лимиты памяти и CPU под нагрузкой,
изоляция через пространства имён, сравнение «контейнер против ВМ».

Связь с лекциями 15–16: домены защиты, права, привилегии; виртуализация,
пространства имён, cgroups, контейнеры.

## Что сделано и как это работает

- **Приложение** (`app/`): сервер-калькулятор из ПР-7. `calc.py` взят без
  изменений (безопасное вычисление через `ast`, без `eval`). Сервер переделан с
  Unix-сокета на TCP (`calc_server.py`), чтобы пробросить порт наружу. Как и в
  ПР-7, каждое подключение обслуживает отдельный процесс (`fork`). Для нагрузочных
  опытов добавлены две служебные команды: `!cpu S` (крутить процессор S секунд) и
  `!mem M` (занять M МБ на 3 секунды, каждая страница реально затрагивается).
- **`app/Dockerfile`**: образ на `python:3.14-slim`. Приложение работает **не от root**:
  создаётся системный пользователь `calc` без пароля, оболочки и домашнего каталога,
  `USER calc`. Файлы кода только для чтения (`0444`).
- **`client.py`**: клиент по TCP; `--load N` запускает N клиентов одновременно.
- **`limits.sh`**: одна и та же нагрузка (4 клиента по `!cpu 6`) без лимитов и с
  `--cpus=0.5 --memory=128m`; снимки `docker stats`; значения cgroup v2
  (`cpu.max`, `memory.max`, `memory.events`) изнутри контейнера; занятие памяти в
  пределах лимита и сверх него.
- **`isolation.sh`**: два контейнера и «наблюдатель» с `--pid=host`: кто какие
  процессы видит, номера пространств имён, имена хостов и IP, файловые системы.
- **`vm_vs_container.sh`**: время запуска контейнера (медиана 10 запусков), время до
  первого ответа сервиса, память контейнера; ресурсы ВМ Docker Desktop и её
  холодный запуск (`docker desktop stop` → `docker desktop start`).
- **`check_pr15.py`**: 13 проверок: сборка, ответы, UID не 0, запрет записи в
  код, значения cgroup, CPU под нагрузкой, OOM, изоляция процессов и пространств имён.

## Среда

macOS 27.0.1 (arm64, 10 ядер), Docker Desktop 4.95 (Docker Engine 29.8.2), ВМ
Docker Desktop с ядром 7.0.14-linuxkit, образ `python:3.14-slim` (Python 3.14.10).
Здесь, в отличие от прошлых работ, скрипты запускаются на **хосте** (macOS), а не
внутри контейнера: они сами управляют контейнерами через `docker`.

## Как запустить

Нужен Docker (на Linux: Docker Engine, на macOS и Windows: Docker Desktop) и `python3`.

```bash
docker build -t pr15-calc app
docker run --rm -d -p 8000:8000 --name calc pr15-calc
./client.py "2 + 2 * 2" "10 / 4"
docker stop calc
```

Вся работа:

```bash
./run.sh
./vm_vs_container.sh        # перезапустит Docker Desktop, только для macOS
```

## 1. Образ и сервис

`evidence/service.txt`:

```text
2 + 2 * 2            -> = 6
10 / 4               -> = 2.5
2 ** 10              -> = 1024
1 / 0                -> ошибка: деление на ноль
__import__('os')     -> ошибка: недопустимое выражение
пользователь: uid=999(calc) gid=999(calc) groups=999(calc)
журнал:
калькулятор слушает порт 8000, PID 1, UID 999
подключение 192.168.65.1:58183, обслуживает PID 7
192.168.65.1:58183: 2 + 2 * 2 -> = 6
```

- Порт 8000 контейнера проброшен на порт 8000 Mac (`-p 8000:8000`), клиент на macOS
  подключается к `127.0.0.1:8000`.
- Внутри контейнера сервер это **PID 1**, а подключение обслуживает дочерний
  процесс PID 7 (fork, как в ПР-7).
- Сервер работает от `uid=999(calc)`. Если в калькуляторе найдётся уязвимость,
  атакующий получит права пользователя без пароля и оболочки, который не может даже
  изменить код приложения (`check_pr15.py` проверяет, что запись в `/app/calc.py`
  запрещена). По умолчанию Docker запускает процесс от root: если такой процесс
  выберется из контейнера (уязвимость ядра или неудачный `-v /:/host`), он будет
  root и на хосте. Поэтому `USER` в Dockerfile обязателен.

## 2. Лимиты памяти и CPU

`evidence/limits.txt`:

```text
== 1. Без лимитов: 4 клиента по «!cpu 6»
calc-free: CPU 400.43%, память 15.24MiB / 7.748GiB

== 2. С лимитами --cpus=0.5 --memory=128m: та же нагрузка
  cgroup внутри контейнера: cpu.max = 50000 100000, memory.max = 134217728
calc-limited: CPU 49.84%, память 15.39MiB / 128MiB

== 3. Память: занять 64 МБ (в пределах лимита) и 300 МБ (больше лимита 128 МБ)
во время !mem 64: память 76.32MiB / 128MiB
!mem 64              -> mem: занято 64 МБ на 3 с
!mem 300             -> (соединение закрыто сервером)
  memory.events: low 0 high 0 max 39 oom 1 oom_kill 1 oom_group_kill 0 sock_throttled 0
  сервер после OOM жив: 6 * 7                -> = 42
```

- **CPU.** Без лимитов 4 процесса-обработчика заняли 4 ядра (400%). С `--cpus=0.5`
  та же нагрузка получила **49,8%**, то есть половину одного ядра на всех. Docker
  записал в cgroup `cpu.max = 50000 100000`: группе разрешено 50 мс процессорного
  времени в каждые 100 мс. Когда квота исчерпана, планировщик ядра просто не даёт
  процессам группы выполняться до следующего периода.
- **Память.** Лимит виден изнутри как `memory.max = 134217728` (128 МБ). Занять 64 МБ
  удалось: память контейнера выросла до 76 МБ из 128. На 300 МБ процесс-обработчик
  был убит OOM-killer внутри cgroup (`oom_kill 1` в `memory.events`), клиент
  увидел закрытое соединение. `--memory-swap=128m` запрещает уходить в своп сверх
  лимита, иначе процесс не убился бы, а начал бы медленно подкачиваться.
- Убит только дочерний процесс, который просил память. Сервер (PID 1) продолжил
  работать и сразу ответил `6 * 7 = 42`: OOM-killer выбирает процесс с наибольшим
  потреблением, а не весь контейнер.
- Остальная система от этого не пострадала: в ВМ 7,7 ГБ, и без лимита эти 300 МБ
  были бы выданы, а с ним контейнер ограничен своими 128 МБ.

## 3. Изоляция

`evidence/isolation.txt`:

```text
== iso-a: процессы, которые он видит
    PID     1  python3 calc_server.py
    PID     7  python3 -c import os
== iso-b: процессы, которые он видит
    PID     1  python3 calc_server.py
    PID     7  python3 -c import os

== Хост (ВМ Docker) глазами контейнера с --pid=host
    всего процессов на хосте: 188
    PID  1115  python3 calc_server.py
    PID  1163  python3 calc_server.py
    iso-a: PID 1 внутри = PID 1115 на хосте
    iso-b: PID 1 внутри = PID 1163 на хосте

== Пространства имён PID 1 (одинаковое число = общее пространство)
  iso-a:
    pid=4026532556  mnt=4026532553  net=4026532558  uts=4026532554  ipc=4026532555
  iso-b:
    pid=4026532692  mnt=4026532689  net=4026532694  uts=4026532690  ipc=4026532691
  хост:
    pid=4026531836  mnt=4026531832  net=4026531833  uts=4026531838  ipc=4026531839

== UTS и сеть: у каждого своё имя и свой IP
    box-a: IP 172.17.0.2
    box-b: IP 172.17.0.3
    iso-a -> iso-b по имени: не видит (gaierror): в сети по умолчанию нет DNS между контейнерами

== mount: файл в /tmp одного контейнера не виден в другом
    iso-a: -rw-r--r-- 1 calc calc 13 Nov 18 10:09 /tmp/only-in-a
    iso-b: ls: cannot access '/tmp/only-in-a': No such file or directory
```

- **PID namespace.** Каждый контейнер видит только 2 процесса: свой сервер (PID 1) и
  саму команду, которой я смотрю список. На хосте в это время 188 процессов, и оба
  сервера там есть, но под номерами 1115 и 1163. Это один и тот же процесс: у него
  есть номер в пространстве имён контейнера (1) и номер в пространстве имён хоста.
  Контейнер не видит ни соседа, ни хоста.
- **Номера пространств имён** у iso-a, iso-b и хоста разные для всех пяти типов: у
  каждого контейнера свои PID, mount, net, UTS и IPC.
- **UTS**: у контейнеров свои имена хостов (`box-a`, `box-b`).
- **Network**: у каждого свой сетевой интерфейс и свой IP (`172.17.0.2` и
  `172.17.0.3`), свой localhost и свои порты: оба сервера слушают порт 8000 без
  конфликта.
- **Mount**: у каждого своя корневая файловая система (слой образа + свой слой для
  записи); файл, созданный в `/tmp` iso-a, в iso-b не существует.

Контейнер это обычный процесс Linux, которому ядро при создании выдало отдельные
пространства имён (что он **видит**) и отдельную cgroup (сколько он может
**потратить**).

## 4. Контейнер против виртуальной машины

`evidence/vm_vs_container.txt`:

```text
== 1. Запуск контейнера (10 раз, медиана)
  docker run --rm pr15-calc python3 -c pass: 204 мс (все: 340 214 203 204 230 193 204 202 199 210)
  от docker run до первого ответа калькулятора: 253 мс
  память работающего контейнера: 11.42MiB
  процессов в контейнере: 1
  размер образа pr15-calc: 204 МБ

== 2. Виртуальная машина Docker Desktop
  память, выделенная ВМ: 7.7 ГБ, процессоров: 10
  ядро ВМ: 7.0.14-linuxkit, процессов внутри ВМ: 187
  резидентная память процесса ВМ на macOS: 1721 МБ
  диск ВМ: 2.4G занято (файл Docker.raw)
  выключаю ВМ: docker desktop stop
  холодный запуск ВМ (docker desktop start -> docker info отвечает): 2.0 с
  первый контейнер после запуска ВМ: 362 мс
```

На macOS контейнеры не могут работать напрямую: им нужно ядро Linux. Docker Desktop
держит маленькую Linux-ВМ (Apple Virtualization.framework), и контейнеры работают
внутри неё. Поэтому на одной машине можно измерить и то и другое.

| | Контейнер | Виртуальная машина (Docker Desktop) |
| --- | --- | --- |
| Время запуска | **0,2 с** (`docker run` до выхода), 0,25 с до ответа сервиса | **2,0 с** холодный запуск ВМ (минимальный LinuxKit); обычная ВМ с Ubuntu в UTM грузится десятки секунд |
| Память | **11 МБ** (один процесс Python) | **1,7 ГБ** резидентной памяти на macOS, выделено 7,7 ГБ |
| Процессы | 1 | 187 (своё ядро, init, системные службы) |
| Диск | 204 МБ образ, общие слои с другими образами | 2,4 ГБ образ диска ВМ |
| Ядро | общее с хостом (здесь с ВМ) | своё |
| Изоляция | пространства имён и cgroups одного ядра | аппаратная виртуализация, отдельное ядро |

**За счёт чего контейнер легче.** ВМ эмулирует целый компьютер: при запуске
загружается собственное ядро, инициализируются виртуальные устройства, стартует init
и системные службы, и всё это держит память, даже когда приложение ничего не
делает. Контейнер ничего не загружает: ядро уже работает, Docker только создаёт
новые пространства имён и cgroup, подключает файловую систему из слоёв образа и
запускает **один процесс** (`fork` + `exec`). Отсюда 0,2 с против секунд и 11 МБ
против гигабайт. Цена: все контейнеры делят одно ядро, и уязвимость ядра опасна
для всех; ВМ отделена надёжнее.

## Контрольные вопросы

**Почему контейнеры запускаются за миллисекунды, а виртуальные машины за секунды?**
Контейнеру не нужно ничего загружать: ядро уже работает. Запуск контейнера это
создание нескольких структур ядра (пространства имён, cgroup), подключение
файловой системы из готовых слоёв и `fork`/`exec` одного процесса. ВМ это
отдельный компьютер: прошивка, загрузка своего ядра, инициализация виртуальных
устройств, init и системные службы. В моём замере 0,2 с против 2,0 с для
минимальной ВМ, а полноценная ВМ с Ubuntu грузится ещё дольше.

**Что общего у контейнера и обычного процесса Linux, и чем контейнер от него
отличается?** Контейнер **и есть** обычный процесс (или группа процессов) на ядре
хоста: на хосте у сервера из iso-a обычный PID 1115, его видно в общем списке
процессов, его планирует тот же планировщик и он делает те же системные вызовы.
Отличия задаёт ядро при создании процесса:
- **пространства имён** ограничивают, что процесс видит: свои PID (он считает себя
  PID 1), свою файловую систему, свою сеть и IP, своё имя хоста;
- **cgroups** ограничивают, сколько он может потратить: CPU (`cpu.max`), память
  (`memory.max`), число процессов;
- плюс ограничения прав: урезанные capabilities, seccomp-фильтр системных вызовов,
  у меня ещё и пользователь не root.

## Типичные ошибки, которых я избегал

- Контейнер и приложение не работают от root: `USER calc` в Dockerfile, это
  проверяется (`UID 999`).
- Лимиты не только заданы, но и проверены под нагрузкой: CPU 49,8% при лимите 50%,
  OOM при попытке занять больше 128 МБ.
- Изоляция показана через пространства имён (номера namespace, PID внутри и на
  хосте), а не только через то, что «в контейнере мало процессов».

## Выводы

- Сервис из ПР-7 упакован в образ на 204 МБ, запускается одной командой, отвечает
  через проброшенный порт и работает от непривилегированного пользователя.
- cgroups надёжно ограничивают контейнер: 4 ядра нагрузки превращаются в 0,5 ядра,
  а попытка занять больше лимита памяти кончается OOM только внутри контейнера.
- Пространства имён дают контейнеру свой взгляд на систему: свои PID, сеть, имя и
  файловую систему; при этом на хосте это обычные процессы.
- Контейнер запускается в 10 раз быстрее даже очень лёгкой ВМ и потребляет память
  одного процесса, потому что не загружает своё ядро; ВМ тяжелее, но изолирует сильнее.
