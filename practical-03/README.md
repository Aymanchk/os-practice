## Задание

Построить дерево процессов текущего пользователя по данным `/proc`.
Создать N дочерних процессов через `fork`, запустить команду через `exec`
и дождаться завершения процессов. Воспроизвести состояния зомби и сироты.
Проверить ленивое копирование памяти после `fork`.

## Дерево процессов

`ptree.py` читает файлы `/proc/PID/status`. Для каждого процесса
определяются PID, PPID, состояние, имя и RSS. Затем процессы текущего
пользователя объединяются в дерево.

Команда `ps` внутри `ptree.py` не используется.

Начало фактического вывода:

```text
Дерево процессов пользователя UID=1000
PID=2316 state=S RSS=16164 kB name=systemd
    PID=2325 state=S RSS=3996 kB name=(sd-pam)
    PID=2345 state=S RSS=6812 kB name=dbus-daemon
    PID=2346 state=S RSS=15648 kB name=pipewire
```

Полный вывод сохранён в `evidence/ptree.txt`.

Состояние `S` означает ожидание, а `R` означает выполнение процесса.
Значение RSS показывает объём резидентной памяти процесса в килобайтах.

## fork, exec и wait

Команда проверки:

```bash
./runner.py 3 sleep 1
```

Фактический результат:

```text
Команда: sleep 1
Количество процессов: 3
Создан процесс 1: PID=8836
Создан процесс 2: PID=8837
Создан процесс 3: PID=8838
Процесс 1: PID=8836, код=0, время=1.006 с
Процесс 2: PID=8837, код=0, время=1.006 с
Процесс 3: PID=8838, код=0, время=1.006 с
Все дочерние процессы завершены
```

Родитель создал три дочерних процесса через `fork`. Каждый ребёнок
заменил свою программу командой `sleep 1` через `exec`. Родитель получил
завершившиеся процессы через `wait` и вывел код возврата и время работы.

Все три процесса завершились с кодом `0`.

При попытке запустить несуществующую команду дочерние процессы завершились
с кодом `127`:

```text
Ошибка exec: [Errno 2] No such file or directory
Процесс 2: PID=8846, код=127, время=0.003 с
Процесс 1: PID=8845, код=127, время=0.004 с
Все дочерние процессы завершены
```

## Процесс-зомби

Фактический вывод `ps` до вызова `waitpid`:

```text
Родитель PID=8857, ребёнок PID=8862
Ребёнок PID=8862 завершается
    PID    PPID S STAT CMD
   8862    8857 Z Z+   [python3] <defunct>
```

Состояние `Z` и отметка `<defunct>` показывают, что ребёнок уже завершился,
но родитель ещё не забрал его код завершения.

После вызова `waitpid`:

```text
waitpid получил PID=8862, код=0
/proc/8862 существует после waitpid: False
```

После `waitpid` запись процесса была удалена из `/proc`, поэтому зомби
не остался в системе.

## Процесс-сирота

Фактический результат:

```text
Промежуточный родитель PID=8892 создал ребёнка PID=8893 и завершается

Ребёнок PID=8893
Первоначальный PPID=8892
Новый PPID=2316, имя усыновителя=systemd
    PID    PPID S STAT CMD
   2316       1 S Ss   /usr/lib/systemd/systemd --user
   8893    2316 S S+   python3 ./orphan_demo.py

Демонстрация сироты завершена
```

Первоначально родителем процесса `8893` был процесс `8892`. После
завершения родителя ребёнок стал сиротой и получил новый PPID `2316`.

В этой системе сироту усыновил пользовательский процесс
`systemd --user`, работающий как subreaper. Поэтому новый PPID оказался
равен `2316`, а не `1`. Сам `systemd --user` является дочерним процессом
системного `systemd` с PID `1`.

## Ленивое копирование памяти

Фактический результат:

```text
Родитель PID=8906 создал список из 8000000 элементов
Родитель до fork: RSS=74612 kB, shared=6340 kB, private=68272 kB
Ребёнок до изменения: RSS=72244 kB, shared=71648 kB, private=596 kB
Ребёнок после изменения: RSS=72692 kB, shared=9492 kB, private=63200 kB
Родитель дождался PID=8909, код=0
```

Сразу после `fork` у ребёнка было `71648 kB` общей памяти и только
`596 kB` приватной памяти. Страницы большого списка не копировались
сразу, а использовались совместно с родителем.

После записи в список общая память уменьшилась до `9492 kB`, а приватная
увеличилась до `63200 kB`. Это подтверждает Copy-on-Write: отдельные
физические страницы создаются при первой записи.

RSS изменился с `72244 kB` до `72692 kB`, то есть только на `448 kB`.
Небольшое изменение RSS ожидаемо, потому что RSS включает и общие,
и приватные резидентные страницы. Для наблюдения Copy-on-Write также
нужно сравнивать значения `shared` и `private`.

## Контрольные вопросы

### Почему fork возвращает два разных значения?

После `fork` выполнение продолжают два процесса. В родительском процессе
`fork` возвращает PID созданного ребёнка, а в дочернем процессе возвращает
`0`. Благодаря разным значениям оба процесса могут определить, какую
ветку программы они должны выполнять.

Если создать процесс не удалось, `fork` сообщает об ошибке и дочерний
процесс не появляется.

### Что изменится, если вызвать exec без предварительного fork?

`exec` заменит текущую программу новой программой. После успешного
`exec` исходная программа больше не продолжит выполнение.

Предварительный `fork` сохраняет родительскую программу. Новая программа
запускается через `exec` только в дочернем процессе, а родитель может
продолжить работу и дождаться ребёнка.
