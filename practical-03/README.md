# ПР-3. Процессы в Linux

**Автор:** Эркинбеков Айман · **Дисциплина:** Операционные системы · **Вариант:** B

## Тема и цель

Наблюдать процессы средствами ОС и управлять ими из программы: создавать
(`fork`), запускать в них другие программы (`exec`), дожидаться (`wait`).
Воспроизвести зомби и сироту и проверить, что память после `fork` копируется
лениво (Copy-on-Write).

## Что сделано и как это работает

- **Дерево процессов без `ps`.** `ptree.py` читает `/proc/<PID>/status` для
  каждого процесса, оставляет процессы текущего пользователя и печатает их
  деревом с отступами: PID, состояние, память RSS, имя.
- **fork + exec + wait.** `runner.py N команда` делает N раз `fork`; каждый
  ребёнок через `execvp` превращается в указанную команду. Родитель ждёт всех
  детей через `wait` и печатает код возврата и время работы каждого. Если
  команда не найдена, ребёнок завершается с кодом 127 (как в shell).
- **Зомби.** В `zombie_demo.py` ребёнок сразу завершается, а родитель секунду
  не вызывает `waitpid`. В это время `ps` показывает ребёнка в состоянии `Z`.
  После `waitpid` запись исчезает.
- **Сирота.** В `orphan_demo.py` промежуточный процесс создаёт ребёнка и сразу
  завершается. Ребёнок через секунду смотрит, кто стал его новым родителем.
- **Copy-on-Write.** `cow_demo.py` создаёт список из 8 млн элементов, делает
  `fork` и сравнивает общую (`shared`) и личную (`private`) память ребёнка
  до и после записи в каждую страницу списка (данные из `/proc/self/smaps_rollup`).

Все скрипты ждут своих детей, поэтому после них не остаётся ни зомби, ни
фоновых процессов, это проверяет последний шаг `run.sh`.

## Как запустить

Нужны `python3` и `ps` из пакета `procps` (`sudo apt install -y python3 procps`).

```bash
./run.sh
```

Или по отдельности, из папки `practical-03`:

```bash
./ptree.py
./runner.py 3 sleep 1
./zombie_demo.py
./orphan_demo.py
./cow_demo.py
```

**Сирота** (ВМ):


Сироту усыновил не PID 1, а `systemd --user` (PID 2316): пользовательский
менеджер служб. Он работает как subreaper («сборщик» осиротевших процессов)
и забирает сирот своей сессии. Сам он ребёнок системного `systemd` с PID 1. В
Docker-контейнере, где `systemd --user` нет, усыновителем становится PID 1
(`docker-init`).

**Copy-on-Write** (ВМ):

```text
Родитель PID=8906 создал список из 8000000 элементов
Родитель до fork: RSS=74612 kB, shared=6340 kB, private=68272 kB
Ребёнок до изменения: RSS=72244 kB, shared=71648 kB, private=596 kB
Ребёнок после изменения: RSS=72692 kB, shared=9492 kB, private=63200 kB
Родитель дождался PID=8909, код=0
```

Сразу после `fork` почти вся память ребёнка общая с родителем (71648 kB):
страницы не копировались. После записи в каждую страницу списка общая память
упала до 9492 kB, а личная выросла до 63200 kB: ядро скопировало страницы
только в момент записи. RSS при этом почти не изменился, потому что он считает
и общие, и личные страницы, для CoW нужно смотреть именно на `shared` и `private`.

## Контрольные вопросы

**Почему fork возвращает два разных значения?** После `fork` код продолжают
выполнять два процесса. Родитель получает PID ребёнка, ребёнок получает 0. По этому
значению каждый понимает, какую ветку программы выполнять. При ошибке ребёнок
не создаётся (в Python `fork` бросает `OSError`).

**Что изменится, если вызвать exec без предварительного fork?** `exec` заменит
текущую программу новой, и исходная программа больше не продолжится, её код
просто исчезнет из процесса. `fork` перед `exec` сохраняет родителя: новая
программа работает в ребёнке, а родитель может дождаться её и продолжить.

## Выводы

- Вся информация о процессах доступна в `/proc`, и дерево процессов можно
  построить без `ps`.
- Связка `fork` + `exec` + `wait`: то, как shell запускает команды; родитель
  обязан забирать детей через `wait`, иначе остаются зомби.
- Сироту усыновляет ближайший subreaper (в Ubuntu Desktop: `systemd --user`),
  а не обязательно PID 1.
- После `fork` память копируется лениво: страница копируется только при
  первой записи в неё.
